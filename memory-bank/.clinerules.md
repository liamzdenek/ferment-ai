# Ferment AI Project Intelligence

This file captures important patterns, preferences, and project intelligence that help work more effectively with the Ferment AI project.

## Project Patterns

### Configuration Patterns

1. **Use AWS CDK Constructs Library**
   - Use the actual "constructs" npm package from AWS CDK
   - Follow the CDK pattern of `new ConstructType(scope, id, props)`
   - Maintain proper scope hierarchy

2. **L1/L2/L3 Construct Hierarchy**
   - L1: Core primitives (VirtualModel, AgentContext, Tool, etc.)
   - L2: Combinations of L1 constructs for common patterns
   - L3: High-level, domain-specific constructs

3. **Package Naming**
   - Use @ferment-ai scope for all packages
   - core-constructs-lib for the core construct library
   - core-constructs-runtime for the runtime implementation of constructs

3. **Declarative Over Imperative**
   - Configuration should be declarative, describing what should exist
   - Runtime logic should be separate from configuration

### Journal Patterns

1. **Journal as Source of Truth**
   - All system state derives from the journal
   - Journal is append-only during execution
   - Events are categorized by type

2. **Event Publishing**
   - Components publish events to the journal
   - No direct state modification
   - Clear event structure with source, target, payload

3. **Event Subscription**
   - Components subscribe to relevant events
   - Derive state from events
   - React to state changes

4. **Modular Journal Implementation**
   - Journal implementation is modularized into specialized manager classes
   - Each manager has a single responsibility
   - JournalImpl delegates operations to these managers
   - Managers include:
     - EventManager: Handles event publication and subscription
     - EventTypeManager: Manages event type registration and validation
     - EntityManager: Handles entity creation and management
     - ComponentManager: Manages components attached to entities
     - SystemManager: Handles system registration and lifecycle
     - ProcessManager: Manages process creation and lifecycle
     - SerializationManager: Handles serialization and deserialization

5. **Event Type Validation**
   - Events have their types validated against registered schemas
   - Errors are published to the journal when validation fails
   - Provides better type safety and error detection

### API Patterns

1. **Completely Stateless API**
   - No server-side state storage
   - Client maintains and passes journal state
   - Each request is self-contained

2. **Streaming Updates**
   - Real-time streaming of events
   - Journal updates included in stream
   - Final journal state returned at completion

3. **Clean Separation of Concerns**
   - API layer separate from execution logic
   - Clear interfaces between components
   - Minimal dependencies

## Known Issues and Workarounds

### 1. TypeScript Module Resolution

**Issue**: When using the 'node16' or 'nodenext' module resolution strategy, TypeScript requires explicit file extensions in import paths.

**Error Message**: 
```
Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './file.js'?
```

**Workarounds**:
1. Add `.js` extensions to all import paths:
   ```typescript
   // Before
   import { Something } from './something';
   
   // After
   import { Something } from './something.js';
   ```

2. Change the module resolution strategy in tsconfig.json:
   ```json
   {
     "compilerOptions": {
       "moduleResolution": "node",
       "module": "esnext"
     }
   }
   ```

### Journal System

The journal system is the central component of the runtime:

1. **Journal Interface**

   ```typescript
   export interface Journal {
     publish(type: EventType | string, source: string, payload: Record<string, any>, target?: string): JournalEvent;
     subscribe(listener: EventListener, filter?: EventFilter): string;
     unsubscribe(id: string): void;
     getEvents(): JournalEvent[];
     // ... other methods
   }
   ```

2. **Journal Implementation**
   ```typescript
   export class JournalImpl implements Journal {
     private eventManager: EventManager;
     private eventTypeManager: EventTypeManager;
     private entityManager: EntityManager;
     private componentManager: ComponentManager;
     private systemManager: SystemManager;
     private processManager: ProcessManager;
     private serializationManager: SerializationManager;

     constructor(options: JournalOptions = {}) {
       // Initialize managers
       this.eventTypeManager = new EventTypeManager(this);
       this.eventManager = new EventManager(this, options.initialState?.events || []);
       this.entityManager = new EntityManager(this, options.initialState?.entities);
       // ... initialize other managers
     }

     // Delegate methods to the appropriate managers
     publish(type: EventType | string, source: string, payload: Record<string, any>, target?: string): JournalEvent {
       return this.eventManager.publish(type, source, payload, target);
     }
     // ... other delegated methods
   }
   ```

## Evolution of Project Decisions

1. **Initial Design**
   - Journal-centric architecture
   - Stateless API
   - Real-time visibility

2. **Key Decisions**
   - Using AWS CDK constructs library
   - Focusing on single-user performance first
   - Prioritizing configuration language and journal design
   - Implementing completely stateless API
   - Renaming package scope from @ferment to @ferment-ai
   - Renaming constructs to core-constructs-lib
   - Creating a separate core-constructs-runtime package
   - Adopting the Entity-Component-System pattern
   - Modularizing the Journal implementation into specialized manager classes

3. **Current Challenges**
   - TypeScript module resolution issues
   - Implementing the HttpApplication in core-constructs-runtime
   - Designing the processor/runtime module interface
   - Ensuring proper event type validation
   - Optimizing serialization for large journals
