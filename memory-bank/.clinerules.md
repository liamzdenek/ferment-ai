# Ferment AI Project Intelligence

This file captures important patterns, preferences, and project intelligence that help work more effectively with the Ferment AI project.

## Project Patterns

### Configuration Patterns

1. **Use AWS CDK Constructs Library**
   - Use the actual "constructs" npm package from AWS CDK
   - Follow the CDK pattern of `new ConstructType(scope, id, props)`
   - Maintain proper scope hierarchy

2. **L1/L2/L3 Construct Hierarchy**
   - L1: Core primitives (VirtualModel, AgentContext, Tool, etc.)
   - L2: Combinations of L1 constructs for common patterns
   - L3: High-level, domain-specific constructs

3. **Package Naming**
   - Use @ferment-ai scope for all packages
   - core-constructs-lib for the core construct library
   - runtime-common for common interfaces and utilities
   - core-constructs-runtime for the runtime implementation of constructs
   - runtime-in-memory for the in-memory implementation of the Journal

4. **Declarative Over Imperative**
   - Configuration should be declarative, describing what should exist
   - Runtime logic should be separate from configuration

### Workflow Patterns

1. **Journal as Central Executor**
   - Journal executes workflows and maintains state
   - Journal is the source of truth for all system state
   - Journal provides serialization/deserialization of state

2. **Workflow Composition**
   - Workflows are composed of tasks with defined relationships
   - Tasks can call other tasks and return to the caller
   - Tasks can call other tasks and not return (like a directed acyclic graph)
   - Workflows are extracted from the construct tree during initialization

3. **Module-Based Mapping**
   - Modules map constructs to task functions
   - Each module is responsible for a specific type of construct
   - Modules are registered with the journal during initialization

4. **Compiler-Based Extraction**
   - Compiler extracts workflows from the construct tree
   - Finds workflow constructs and their tasks
   - Creates workflows from entrypoints if no workflow constructs are found

### API Patterns

1. **Completely Stateless API**
   - No server-side state storage
   - Client maintains and passes journal state
   - Each request is self-contained

2. **Streaming Updates**
   - Real-time streaming of events
   - Journal updates included in stream
   - Final journal state returned at completion

3. **Clean Separation of Concerns**
   - API layer separate from execution logic
   - Clear interfaces between components
   - Minimal dependencies

## Known Issues and Workarounds

### 1. TypeScript Module Resolution

**Issue**: When using the 'node16' or 'nodenext' module resolution strategy, TypeScript requires explicit file extensions in import paths.

**Error Message**: 
```
Relative import paths need explicit file extensions in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'. Did you mean './file.js'?
```

**Workarounds**:
1. Add `.js` extensions to all import paths:
   ```typescript
   // Before
   import { Something } from './something';
   
   // After
   import { Something } from './something.js';
   ```

2. Change the module resolution strategy in tsconfig.json:
   ```json
   {
     "compilerOptions": {
       "moduleResolution": "node",
       "module": "esnext"
     }
   }
   ```

### Workflow System

The workflow system provides the foundation for executing agent operations:

1. **Workflow Class**
   ```typescript
   export class Workflow extends Construct {
     private readonly definition: Workflow.Task;

     constructor(scope: Construct, id: string, options: WorkflowOptions) {
       super(scope, id);
       this.definition = options.definition;
     }

     getDefinition(): WorkflowDefinition {
       const tasks: Record<string, TaskDefinition> = {};
       const entryPoints: Record<string, string> = {
         'default': this.definition.node.id
       };

       // Add the entry point task
       tasks[this.definition.node.id] = this.definition.getDefinition();

       // Add all tasks reachable from the entry point
       this.addReachableTasks(this.definition, tasks);

       return {
         id: this.node.id,
         name: this.node.id,
         description: this.options.description,
         tasks,
         entryPoints
       };
     }
   }
   ```

2. **Task Class**
   ```typescript
   export class Task extends Construct {
     private readonly nextTasks: Task[] = [];
     private readonly tools: Record<string, Task> = {};

     constructor(scope: Construct, id: string, options = {}) {
       super(scope, id);
     }

     canCall(task: Task): this {
       this.nextTasks.push(task);
       return this;
     }

     canCallAndReturn(tool: Task): this {
       const toolId = tool.node.id;
       this.tools[toolId] = tool;
       return this;
     }

     sendEmailTool(): Task {
       const tool = new Task(this, `${this.node.id}SendEmailTool`, {
         description: `Send an email to ${this.node.id}`
       });
       return tool;
     }
   }
   ```

### Journal System

The journal system is the central component of the runtime:

1. **Journal Interface**
   ```typescript
   export interface Journal {
     executeWorkflow(workflowName: string, input?: any): AsyncIterable<WorkflowLogEvent>;
     toSavedState(): JournalState;
     fromSavedState(state: JournalState): void;
     addModule(module: Module): void;
   }
   ```

2. **Journal Implementation**
   ```typescript
   export class Journal implements JournalInterface {
     private readonly workflows: Map<string, WorkflowDefinition> = new Map();
     private readonly taskFunctions: TaskFunctionMap = {};
     private readonly executors: Map<string, WorkflowExecutor> = new Map();

     constructor(private readonly modules: Module[], options: JournalOptions & { rootConstruct: RootConstruct }) {
       // Compile workflows from the root construct
       const result = compileWorkflows({
         rootConstruct: options.rootConstruct,
         modules: this.modules
       });

       // Store the compiled workflows and task functions
       this.initializeFromCompileResult(result);
     }

     async *executeWorkflow(workflowName: string, input?: any): AsyncIterable<WorkflowLogEvent> {
       // Get the workflow executor
       const executor = this.executors.get(workflowName);
       if (!executor) {
         throw new Error(`Workflow not found: ${workflowName}`);
       }

       // Execute the workflow
       for await (const event of executor({ entryPoint: 'default', input })) {
         yield event;
       }
     }
   }
   ```

3. **Module Interface**
   ```typescript
   export interface Module {
     (construct: Construct): TaskFunction | undefined;
   }
   ```

## Evolution of Project Decisions

1. **Initial Design**
   - Journal-centric architecture
   - Stateless API
   - Real-time visibility

2. **Key Decisions**
   - Using AWS CDK constructs library
   - Focusing on single-user performance first
   - Prioritizing configuration language and journal design
   - Implementing completely stateless API
   - Renaming package scope from @ferment to @ferment-ai
   - Renaming constructs to core-constructs-lib
   - Creating a separate core-constructs-runtime package
   - Adopting a workflow-based architecture
   - Implementing the Journal as a workflow executor
   - Creating a module system for mapping constructs to task functions
   - Implementing a compiler to extract workflows from the construct tree

3. **Current Challenges**
   - TypeScript module resolution issues
   - Implementing real agent execution
   - Designing the task function interface
   - Ensuring proper workflow execution
   - Optimizing serialization for large journal states
